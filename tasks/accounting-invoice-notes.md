# Invoice build working notes

Source inspection after SimpleFIN commit `9e12bb1`:

- `app/supabase/schema.sql` is the CRM canonical schema. Invoices are `project_invoices`; `line_items` is one JSONB column, so the current invoice row trigger already sees updated line items atomically. No separate line-item table is involved.
- `projects.tax_rate` is applied at PDF generation time in `app/src/lib/invoice-pdf/buildInvoiceData.ts`; `project_invoices.amount` is the subtotal. Customer identity comes from `project_contacts.is_primary_client` joined to `contacts`. Source lifecycle must preserve the observed subtotal, tax calculation/context, current customer/project identity and full revision, and flag incomplete historical reconstruction. Do not assume invoice.amount includes sales tax.
- Current `emit_invoice_webhook` only produces paid/updated/deleted paid-relevant events. Keep it and the admin personal-income receiver intact. Add a separate `invoice.lifecycle` event with string revision and exact string cents. The dedicated accounting receiver will use a durable inbox and never turn a CRM paid flag into a posting.
- Current `claim_webhook_deliveries` + Node dispatcher attempts each delivery once. Add fenced leases and bounded retries for the new lifecycle event. Preserve legacy failed-delivery manual behavior. The new accounting receiver handles concurrent and out-of-order deliveries atomically.
- CRM app has a service client helper and permission `webhooks.manage`. API middleware implementation still needs inspection before adding secret-authenticated internal snapshot and scheduled dispatch endpoints. Do not touch .env or activate real source endpoints/jobs.
- No repository AGENTS.md was found. No subagents are authorized. User requires Codex browser and prohibits Playwright.

Proposed source packet (not implemented yet):

1. Private source settings with persistent source UUID; current invoice heads plus immutable per-invoice revisions/tombstones. A source-level transaction lock acquired by BEFORE STATEMENT triggers on invoice/project/contact/primary-contact changes avoids sequence/commit-order assumptions and permits a consistent materialized snapshot. Only relevant metadata changes emit new invoice revisions. Keep original source update/deletion payloads and mark bootstrap history separately.
2. Capture all invoice states, including draft, sent, overdue, paid, cancelled, and deleted. Source validation must retain a visible issue rather than prevent unrelated CRM invoice editing when old data has missing IDs, malformed dates, unsupported lines, or disagreeing totals. Cash posting remains blocked by admin review for invalid records.
3. Snapshot start refreshes heads against all current invoices and detects disappeared records, then materializes every head and tombstone under the source lock. A UUID token freezes paging; byte-bounded pages and a count/manifest hash verify complete delivery. Source per-invoice versions, not a global SQL sequence cursor, govern convergence. Transient snapshot objects may expire; permanent revision/tombstone evidence stays.
4. A service-role-only snapshot RPC and secret-authenticated internal Node endpoint. `ACCOUNTING_INVOICE_SYNC_SECRET` and a fixed configured CRM URL will be server-only. Accounting will store snapshot/run progress and periodically pull a complete snapshot, with worker scheduling off until configured and owner enabled.
5. New lifecycle payloads carry schema version, persistent source ID, stable event ID, invoice ID, revision string, observed time, hash and serialized source body. Exact source serialization permits cross-runtime hash verification. Initial bootstrap never fabricates earlier issue/amendment history. Current source invoices can be listed while old as-of aging is explicitly incomplete.
6. Add delivery attempt token/expiry and next-attempt time. Complete via a fenced RPC. New lifecycle errors retry with bounded backoff; old legacy failures retain manual resend semantics. Manual requeue should use a permission-checked command. Outbound delivery should refuse redirects, bound response reads, and protect network destinations. No real delivery is executed in acceptance.
7. Test source SQL in a synthetic minimal CRM fixture built from the relevant actual table shapes, including per-invoice revisions, duplicate/no-op edits, unpaid/cancel/delete, project/customer changes, snapshot consistency across pages, missed-trigger convergence, exact tax/subtotal differences, permissions, leases and retries. Package one new app migration, canonical definitions edited in place, then commit separately from the later admin migration.
